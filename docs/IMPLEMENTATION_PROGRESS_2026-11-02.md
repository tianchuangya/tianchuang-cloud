# TC Cloud Warehouse 实施进度

日期：2026-11-02  
工程基线：`docs/warehouse-sync-engineering.md`

## 本轮已完成

### Warehouse 与恢复

- 新增真实共享 Warehouse Git 提供器。多个资料库共用一个仓库和缓存，分别写入 `libraries/<library-id>/files` 与 `.tc-cloud/libraries/<library-id>.json`。
- 以远端地址和分支为粒度串行化仓库操作，避免多个资料库同时拉取、提交和推送互相踩踏。
- 创建目标时默认提供“主 Warehouse”，Warehouse 名称默认为 `TC-cloud-Warehouse` 且允许修改。
- 可发现带 Warehouse topic 或描述标识的自定义名称仓库；新设备按稳定 library ID 恢复。
- 删除单个资料库的 Warehouse 备份时只删除对应目录和状态，不删除共享仓库或其他资料库。

### 同步状态与冲突

- `electron/sync-state.ts` 使用16字节密码学随机数生成32位小写十六进制 revision ID。
- 状态包含父版本、generation、设备 ID、SHA-256、稳定文件 ID、删除墓碑和目标确认版本；兼容旧 manifest。
- 每个同步目标拥有独立基线，某一目标成功不会破坏其他目标的冲突判断。
- Git、Warehouse、本地镜像和 WebDAV 均在执行前复核远端指纹；计划有效期最长2分钟。
- 同一资料库执行互斥，自动同步同一资料库去重；远端在规划后变化时自动重新规划一次。
- 普通 Git、Warehouse、WebDAV 和磁盘镜像执行前同时复核本地与远端；确认期间新增删除或编辑会废弃旧计划，自动同步按正常并发事件重规划而不先弹失败。
- 文件扫描始终计算 SHA-256，修复“大小和 mtime 相同但内容变化”被漏掉的问题。
- 修复本地镜像选择“以远端为准”时没有真正回写本机的问题。
- 自动同步遇到已拔出的移动盘、离线 NAS 或不存在的源目录时静默等待，不再周期性弹出 ENOENT；手动同步仍保留明确错误。

### 连接、设备与安全

- 新增全局存储连接。旧资料库目标会惰性迁移为连接，新资料库可直接复用 Git、WebDAV 或磁盘连接。
- 设置页展示全局连接；添加目标弹窗提供“直接绑定”。移除资料库时不会误删仍被其他资料库或全局连接引用的 WebDAV 密钥。
- 首次运行生成稳定32位设备 ID；设备文档按 `.tc-cloud/devices/<device-id>.json` 保存，记录名称、型号、平台、版本、最近活跃和同步状态。
- 发布前检查设备名称唯一；相同 device ID 会恢复已有设备名称。
- `safeStorage` 不可用时拒绝保存或读取秘密，不再回退为可逆 Base64 明文。
- 多云迁移先检查源目标；源目标与本机未对齐时阻止迁移，避免把过期本机副本冒充云到云迁移源。

### WebDAV 与界面

- WebDAV 密码由服务层注入，提供器不再直接依赖 Electron store，便于隔离测试。
- 协议 mock 覆盖同大小内容变化、远端独有文件下载和过期计划拒绝。
- Warehouse 故障注入覆盖服务端拒绝 push：远端未确认时不推进本机状态或目标基线。
- 目标弹窗改为固定头尾、内容区滚动；在 1240×790 实际 Electron 窗口中确认底部操作按钮完整可见。
- 已逐项查看“账户与设备”和“添加同步目标”界面，确认 Warehouse、设备、全局连接与目标模式均真实显示。

## 仍未完成，不能宣称已实现

1. **应用级账户与社交身份绑定**：X/Twitter、YouTube/Google、Facebook 需要 OAuth 应用、回调域名、隐私政策和服务端账户映射；现有 GitHub 多账号是存储身份，不等于天创云端统一账户。
2. **实时在线设备状态**：Git 仓库只能表示 `lastSeenAt`，真正在线状态需要心跳或 WebSocket 服务。
3. **私人服务器原生协议**：已挂载 NAS 和自托管 WebDAV 可用；SFTP、S3/OSS 原生提供器尚未确定和实现。
4. **全局连接生命周期**：已支持迁移、查看、创建和复用，但连接编辑、删除、失效检测及凭据轮换界面未完成。
5. **真实服务兼容矩阵**：WebDAV mock 已覆盖核心差异与过期计划，但 Nextcloud、群晖、坚果云等真实服务的配额、锁定、断网恢复和原子移动差异仍需发布前验证。
6. **完整故障注入**：进程在文件传输中途被杀、磁盘写满、Git push 后状态发布失败、超大 Warehouse 历史清理等场景仍需专项测试。

## 后续建议顺序

1. 增加中断与磁盘写满故障注入，验证临时文件、恢复副本和重试幂等性。
2. 实现全局连接编辑、删除、健康检查与凭据轮换。
3. 用至少两个真实 WebDAV 服务跑兼容矩阵；之后再决定是否增加 SFTP 或 S3。
4. 应用级账户、社交 OAuth 和实时心跳应作为独立后端项目推进，不应在桌面端做假绑定入口。
